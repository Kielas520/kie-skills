**填写要求**

填写本模板时，借鉴 RFC 的规范性写法，遵循以下要求。这些要求约束填写内容

1. 术语一致。同一概念使用同一名称；有歧义的术语或缩写在首次出现时解释。
2. 行为明确。接口与关键流程写清“哪个组件，在什么条件下，执行什么动作，产生什么可观察结果”。
3. 要求强度明确。“必须／不得”表示强制要求或禁止；“应／不应”表示推荐，存在充分理由时可例外，并说明影响；“可以”表示可选行为。仅在需要约束行为时使用，不为普通说明机械添加关键词。
4. 边界明确。对本次变更涉及的缺省输入、错误、重复、并发、超时或重试，规定处理结果及可能的副作用。与本次变更无关的情况不必展开。
5. 区分约定与实现。
6. 可验证且不隐瞒未决问题。

参考：RFC Editor 的 RFC 阅读说明 https://www.rfc-editor.org/series/rfc/ 。

**本地补充要求**

以上内容与团队知识库的技术方案模板保持一致（不含第 9 节 Review 与评论）。以下是本地写 `design.md` 时追加的要求：

1. 同一个事实只写一处。完整签名、字节布局、字段表只在「4. 详细设计」写全，其他章节写一句要点或指回该节；交付前逐节找同一个细节的第二次出现，删到只剩一处。
2. 变更记录默认只留初始版本那一行。设计方案打了新版本才追加记录；要不要打版本先问用户，用户确认后才追加，不打版本就不写。
3. 全文控制在 250 行以内。删重之后仍然超出时，在交付说明里点出是哪一节、为什么长。
4. 数据链路用 mermaid 画，放在「4. 详细设计」里，让读者看清数据从哪来、经过哪些环节、到哪去。给已有工程加功能时，用不同样式标出本次新增的环节与改动到的已有环节，并写明新功能插在链路的哪个位置。一张图只说明一件事；涉及跨进程或跨设备的先后顺序时，另用 `sequenceDiagram` 画时序。

```mermaid
flowchart LR
    A[输入] --> B[现有环节]
    B --> C[本次新增环节]
    C --> D[输出]
    classDef added fill:#d4f4dd,stroke:#2e7d32
    class C added
```
