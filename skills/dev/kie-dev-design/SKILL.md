# 技术设计文档

方案选定之后，把方案展开成可实施的技术设计文档。产出物只有一份：`~/project/<项目名称>/.idea/design.md`，本技能不改业务代码。

## 前置条件

`~/project/<项目名称>/.idea/solver.md` 存在，且用户已在某个方案标题处标注选定，或用户在对话里明确了选哪条路。

方案没定（`solver.md` 缺失、或没有任何方案被选定）时不要开始写设计文档，先走 `kie-dev-solution`：`solver.md` 缺失会让设计文档没有取舍依据，直接写就等于替用户选了方案。

## 写文档

读 `assets/技术方案模板.md`，按模板章节逐节填，不增删模板的章节层级。各节要点：

- 背景与目标：现状问题用数据说清，目标每条只写一件能被衡量的事，非目标写明不做的事与不做的原因。
- 接口与行为约定：写返回值含义、前置条件、错误语义、幂等性；没有对外接口变更写「不适用」。
- 方案与取舍：把 `solver.md` 里选定的方案展开进详细设计；未选中的方案在表里保留一行，写清不选的原因；试过行不通的路径记录当时的现象。
- 详细设计：写到符号名这一级，API 给出签名，协议给出字节布局，状态机用表；已有工程按「仓 — 层 / 模块（路径）」分小节。
- 接口变更清单、兼容性与影响面、风险评估与应对、测试用例：按模板表格填，与本次变更无关的行删掉。
- 变更记录：默认只留初始版本那一行。用户要求写变更记录时才追加行。

## 数据链路

用 mermaid 画数据链路，让用户看清数据从哪来、经过哪些环节、到哪去。

给已有工程加功能时，图中用不同样式标出本次新增的环节与改动点，并写明新功能插在链路的哪个位置；改动到已有环节的，标出被改的环节。

```mermaid
flowchart LR
    A[输入] --> B[现有环节]
    B --> C[本次新增环节]
    C --> D[输出]
```

涉及跨进程或跨设备的先后顺序时改用 `sequenceDiagram` 画时序，一张图只说明一件事。

## 交付与审核

写完把文件路径给用户，等用户审核。用户提出更改需求时：

1. 直接改 `design.md` 对应章节，一次改到位。
2. 只呈现最终状态：不保留旧写法，不写「原先写的是…现在改成…」，不擅自加版本号或变更记录行。
3. 用户明确要求写变更记录时，才在变更记录表里追加一行。
4. 改完再交用户审核，直到用户确认。

用户确认设计后，按 `design.md` 开始实现走 `kie-dev-execute`。

## Gotchas

- 方案文档回答「走哪条路」，设计文档回答「这条路怎么走」。设计文档里不再做方案选型，选型结论来自 `solver.md`。
- 用户拿方案文档里的取舍意见回来要求改设计时，先确认选定的还是原方案；换方案就要先回 `solver.md` 更新选定标注。
- 画图用 mermaid，不用 ASCII 画示意与表格。
- `design.md` 与 `solver.md` 同在 `<项目>/.idea/` 下，`.idea/` 里其他配置文件不动。
