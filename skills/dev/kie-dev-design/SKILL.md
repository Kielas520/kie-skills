# 技术设计文档

把已经选定的方案展开成可实施的技术设计文档。本技能不改业务代码。`<项目名称>` 与 `<任务>` 的取值、文档目录的落点见 `kie-agent-rules` 技能目录下的 `references/workspace.md`。

## 子能力

| 子能力 | 产出 | 何时做 |
| --- | --- | --- |
| 写设计文档 | `.idea/<任务>/design.md` | 用户要求写设计文档时 |
| 按审核意见修改 | 改好的 `design.md` | 用户对设计文档提出修改意见时 |

每个子能力做不做由用户决定。

## 设计依据

设计文档回答「选定的这条路怎么走」，不在设计文档里重新选方案。动笔前先找依据：

1. 在同一任务目录 `.idea/<任务>/` 下找 `solve.md`（已确认的方向）。需要对照取舍来历时，再读同目录的 `solution.md`。
2. 用户在对话里直接说明了选哪条路时，以用户说的为依据。
3. 两者都没有：问用户设计依据在哪里，依据到手之前不写 `design.md`。

用户的修改意见改变了选定的方案时，说明设计依据变了，问用户要不要先更新依据文档；本技能不改 `solve.md` 与 `solution.md`。

## 写设计文档

模板是 [assets/design.md](assets/design.md)：章节、顺序、表头与写法都按模板来，包括末尾的「填写要求」与「本地补充要求」。以 `<>` 标出的占位、「填写要求」与「本地补充要求」都是填写说明，不抄进产出物。

写到 `~/kie-ws/<项目名称>-p/.idea/<任务>/design.md`，只写自己任务目录下的文档，不动同级其他任务目录。写完把文件路径给用户审核。

## 按审核意见修改

1. 直接改 `design.md` 对应章节，一次改到位，不保留旧写法。
2. 变更记录与版本号按模板的「本地补充要求」处理。
3. 改完再交用户审核，直到用户确认。

## Gotchas

- `assets/design.md` 与团队知识库的技术方案模板保持同步，只去掉第 9 节 Review 与云文档上的评论；「本地补充要求」是本地追加的部分，不属于云上模板。云上模板变了，按它更新 `assets/design.md` 时保留「本地补充要求」。
