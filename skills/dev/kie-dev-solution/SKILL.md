# 开发前的调研与方案选型

用户提出要做的功能之后，先调研，再产出方案文档交用户选定。产出物只有一份：`~/project/<项目名称>/.idea/solver.md`，本技能不改业务代码。

## 情况判断

| 情况 | 做法 |
| --- | --- |
| 从零开始的新项目 | 调研同类实现、库与框架选型、落地路径 |
| 已有工程加功能 | 除调研外，读现有代码实现，定位改动位置 |
| 用户已选定方案 | 不适用本技能，转 `kie-dev-design` 写设计文档 |
| 用户要求直接改代码 | 不适用，需求已经明确到怎么做 |

## 调研

无论需求轻重都先调研，不允许跳过调研直接给方案。

| 需求 | 手段 |
| --- | --- |
| 网页、官方文档、社区讨论 | `web_search` 找入口，`read` 读完整页面；用户给了链接就先把链接内容读完 |
| 库与框架的 API | 会话里配置了 Context7 就用它查，否则直读官方文档与本地依赖源码（Rust 依赖在 `~/.cargo/registry/src/`） |
| 学术文献 | `paper-search search "<关键词>"` |
| 同类项目与 issue | `gh search repos`、`gh search code`、`issue://`、`pr://` |
| 已有工程的实现 | 读相关模块，用 `xd://lsp` 的 references 查受影响的调用点 |

调研结论要落到事实：库名与版本、API 签名与前置条件、性能与限制、许可协议、最近的活跃程度。拿不准的写明不确定在哪，不猜，不编造参考文献。

## 方案文档

写到 `~/project/<项目名称>/.idea/solver.md`，`.idea/` 不存在就创建，不动该目录下其他文件。

```markdown
# <功能名称> 方案调研

## 要实现的功能
<要达成什么，验收条件是什么>

## 项目现状
<已有工程写清当前实现与相关模块；新项目写清可复用的东西>

## 方案一：<名称>（风险 <低/中/高>）
### 方案细节
<怎么实现>
### 涉及的改动位置
| 文件 | 符号 | 改动 |
| --- | --- | --- |
### 风险评估
- 改动量：<改多少文件、多少行，是否动到对外接口>
- 实现复杂度：<难在哪，依赖哪些没验证过的能力>
- 可维护性：<后人接手要懂多少东西>
- 风险：<失败模式、兼容性、不可逆的部分>
### 参考文献
- <实际读过的链接>

## 方案二：<名称>（风险 <低/中/高>）
<同上>
```

- 方案数量由调研结果定。只有一个可行路径时只写一个，说明没有别的路径的原因。
- 按风险从低到高排，第一条是风险最低的。
- 给已有工程加功能时，每个方案都要写到文件与符号一级。
- 风险评估四项固定写全，四项都不适用就写「不适用」并说明理由。

## 交付与审核

1. 写完把文件路径与方案摘要给用户，等用户选定。不替用户选方案。
2. 用户选定后，回到 `solver.md` 在选定方案的标题处标注已选，文档其余内容不动。
3. 用户对全部方案都不满意，或选定后对方案提了新意见：按意见改 `solver.md` 里该方案的描述，再交用户重新审核。
4. 用户确认方案后转 `kie-dev-design` 写设计文档；设计文档确认后按它实现走 `kie-dev-execute`。

## Gotchas

- 「先调研一下」「怎么实现比较好」是咨询类指令：只产出方案文档，不顺手改代码。
- `.idea/` 是 IDE 配置目录，只创建与写入 `solver.md`，不改其下的配置文件。
- 方案排序按风险从低到高。用户要求换排序时按用户说的排，正文注明排序依据。
- 用户选定方案后回到 `solver.md` 在标题处标注，未选中的方案保留下来作为取舍记录。
- 项目名以用户给的为准；用户没说就按当前工作目录的仓库名。
