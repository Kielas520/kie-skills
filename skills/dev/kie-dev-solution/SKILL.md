# 开发前的调研与方案选型

用户提出要做的功能之后，先把源仓库备齐，再调研，最后产出选型文档交用户选定。产出两份文档，都在 `~/kie-ws/<项目名称>-p/.idea/<任务>/` 下：

| 文档 | 何时产出 | 内容 |
| --- | --- | --- |
| `solution.md` | 调研结束 | 项目现状 + 全部候选方案（含方案细节、改动位置、风险评估、参考文献），不含选定标记 |
| `solve.md` | 用户拍板后 | 只记已确认的方向，模板见 [references/solve.md](references/solve.md)，交 `kie-dev-design` 写 `design.md` |

用户拍板时不新建文档，只在 `solution.md` 里对应方案的标题处标注选定。本技能不改业务代码。`<项目名称>` 与 `<任务>` 的取值见 `kie-agent-rules` 的工作空间约定。

## 准备源仓库

调研要读真实代码，动手前确认源仓库已经克隆，并与最新 main 同步：

```bash
git -C ~/kie-ws/<项目名称>-p/source/<仓库名> fetch origin
git -C ~/kie-ws/<项目名称>-p/source/<仓库名> rev-list --count main..origin/main
```

| 情况 | 做法 |
| --- | --- |
| 目录不存在 | 克隆到 `~/kie-ws/<项目名称>-p/source/<仓库名>`，父目录不存在先建；单个仓库用 `git clone <地址> <路径>`，按 owner/repo 查找用 `gh repo clone <owner>/<仓库名> <路径>` |
| 目录存在 | 先 `git fetch origin`，再确认 main 相对 `origin/main` 落后多少 |
| main 落后且工作区干净 | 切到 main 后 `git merge --ff-only origin/main`，落后的 commit 数写进方案文档的「项目现状」 |
| 工作区有未提交改动，或停在别的分支 | 不动它，把当前分支、未提交的文件与落后的 commit 数报给用户，等用户决定 |

- 一份克隆服务调研、设计与后续工作区，不重复克隆，也不把仓库克隆到项目容器之外。
- 不切换、不清理用户已有的分支与改动；要看其他分支的实现用 `git show origin/main:<文件>`，需要完整工作区时开 worktree。
- 项目名以用户给的为准；用户没说就取 `git worktree list --porcelain` 第一行的目录名，当前目录就是仓库根时即该目录名。仓库名取 `origin` 地址的最后一段。

## 情况判断

| 情况 | 做法 |
| --- | --- |
| 从零开始的新项目 | 调研同类实现、库与框架选型、落地路径 |
| 已有工程加功能 | 除调研外，读现有代码实现，定位改动位置 |
| 用户已选定方案 | 不适用本技能，转 `kie-dev-design` 写设计文档 |
| 用户要求直接改代码 | 不适用，需求已经明确到怎么做 |

## 调研

无论需求轻重都先调研，不允许跳过调研直接给方案。

| 需求 | 手段 |
| --- | --- |
| 网页、官方文档、社区讨论 | `web_search` 找入口，`read` 读完整页面；用户给了链接就先把链接内容读完 |
| 库与框架的 API | 会话里配置了 Context7 就用它查，否则直读官方文档与本地依赖源码（Rust 依赖在 `~/.cargo/registry/src/`） |
| 学术文献 | `paper-search search "<关键词>"` |
| 同类项目与 issue | `gh search repos`、`gh search code`、`issue://`、`pr://` |
| 已有工程的实现 | 读相关模块，用 `xd://lsp` 的 references 查受影响的调用点 |

调研结论要落到事实：库名与版本、API 签名与前置条件、性能与限制、许可协议、最近的活跃程度。拿不准的写明不确定在哪，不猜，不编造参考文献。

## 产出时机

- 写 `solution.md`、`solve.md` 需要用户明确的开工指令（「出个方案」「写选型文档」「去调研并落盘」）。只回答要改什么、只讨论文档口径、只要求先确认，都不写文件、不建 `.idea/<任务>/`。
- 技能被加载或被调用不构成开工指令：本技能正文与 description 里的文档名、落点、模板只定义产出物的形态与位置，不定义什么时候写。
- 已有拍板记录不等于对本次写入的授权。用户拿已选定的文档回来提意见，或问「要不要改」时，先给改动清单等回应，不因为「已经拍过板」就直接改文档或重建文档。
- 同一次任务里用户已明确要求改动的直接改，不重复确认；范围不清楚时先问一句，不先写文件。

## 方案文档

### `solution.md`

写到 `~/kie-ws/<项目名称>-p/.idea/<任务>/solution.md`，内容为项目现状与全部候选方案，不带选定标记。用户拍板后回到这份文档，在对应方案的标题处标注选定（如 `## 方案二：<名称>（已选定）`），其余内容不动，未选中的方案保留下来作为取舍记录。

```markdown
# <功能名称> 选型文档

## 要实现的功能
<要达成什么，验收条件是什么>

## 项目现状
<已有工程先讲清原有设计的技术原理：这套机制是什么、覆盖与不覆盖哪些范围、数据从哪来到哪去、每个环节与函数各做什么；再写与本次改动直接相关的现状要点。新项目写清可复用的东西>

## 方案一：<名称>（风险 <低/中/高>）
### 方案细节
<怎么实现>
### 涉及的改动位置
| 文件 | 符号 | 改动 |
| --- | --- | --- |
### 风险评估
- 改动量：<改多少文件、多少行，是否动到对外接口>
- 实现复杂度：<难在哪，依赖哪些没验证过的能力>
- 可维护性：<后人接手要懂多少东西>
- 风险：<失败模式、兼容性、不可逆的部分>
### 参考文献
- <实际读过的链接>

## 方案二：<名称>（风险 <低/中/高>）
<同上>
```

- 「项目现状」开头讲清原有设计的技术原理，写到环节与函数职责这一级。调研时手上已有的链路说明、草稿这类素材，原有设计内容要承接到这一节里，不能只压成文件与符号清单。
- 方案数量由调研结果定。只有一个可行路径时只写一个，说明没有别的路径的原因。
- 按风险从低到高排，第一条是风险最低的。
- 给已有工程加功能时，每个方案都要写到文件与符号一级。
- 风险评估四项固定写全，四项都不适用就写「不适用」并说明理由。

### `solve.md`

用户在 `solution.md` 上拍板后写到同目录，只记录已确认的方向，按 [references/solve.md](references/solve.md) 的模板组织，供 `kie-dev-design` 写 `design.md` 使用。取舍过程与未选方案留在 `solution.md`，这份不重复抄录。原有设计原理在这份里保留要点（这套机制是什么、覆盖范围、数据链路、本次改动碰到的环节），粒度低于 `solution.md` 的「项目现状」，不复述函数级职责与使用须知。

`.idea/<任务>/` 不存在就创建，只写自己任务目录下的文档，不动同级其他任务目录与其他文件。

## 交付与审核

1. 写完把文件路径与方案摘要给用户，等用户拍板。不替用户选方案。
2. 用户拍板后，回到 `solution.md` 在选定方案的标题处标注已选，文档其余内容不动；随后按 `references/solve.md` 的模板产出 `solve.md`。
3. 用户对全部方案都不满意，或拍板后又提了新意见：按意见改 `solution.md` 里该方案的描述，再交用户重新审核；已产出 `solve.md` 的同步更新。
4. `solve.md` 出好并经用户确认后转 `kie-dev-design` 写设计文档；设计文档确认后按它实现走 `kie-dev-execute`。

## Gotchas

- 「先调研一下」「怎么实现比较好」是咨询类指令：只回答与评估，不产出也不修改任何文档；等用户给出开工指令再写。
- `.idea/` 位于项目容器里，不在仓库内，不随分支切换变化，也不参与版本控制；文档按任务分目录，并行任务互不覆盖。
- 方案排序按风险从低到高。用户要求换排序时按用户说的排，正文注明排序依据。
- 用户拍板后回到 `solution.md` 在标题处标注，未选中的方案保留下来作为取舍记录；`solve.md` 只写已确认的方向，不重复整份取舍过程。
- 技能被调用、用户查看或核对本技能该做什么，都不构成开工指令；用户要求先确认要改什么时，先给改动清单等回应，不先落盘。
