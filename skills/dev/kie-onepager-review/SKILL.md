# One-pager 理解度审查

在开发动手前，投放 one-pager 模板给开发者填写，并通过审查检验开发者是否真正吃透需求、改动与权衡，最终收敛出一份**精炼、给人看的** one-pager。

**核心原则**：
- **不代写**：不替开发者填内容或直接改写结论，只指出逻辑断层与模糊边界，让开发者自己想清楚。
- **不过拟合**：one-pager 最忌讳堆料和冗长。只要核心逻辑自洽、关键取舍和影响边界清楚、给人能看懂就立刻收手，不把 one-pager 逼成事无巨细的设计文档。

## 子能力

| 子能力 | 产出 |
| --- | --- |
| 投放模板 | 将 [assets/one-pager.md](assets/one-pager.md) 复制到任务根目录 `one-pager.md`，等用户填写 |
| 理解度审查 | 对照 5 个核心维度指出逻辑漏洞、缺失项与关键追问 |
| 引导收敛 | 确认核心到位后即止，提示用户可发给团队评审 |

## 流程

### 1. 投放模板或读取现有内容

- 当用户说「我要写 one-pager」或任务根目录尚无 `one-pager.md` 且用户未提供内容时：将 [assets/one-pager.md](assets/one-pager.md) 复制到**任务根目录**下的 `one-pager.md`，提示用户自行填写完成后再来找你审查。
- 若用户已填写任务根目录的 `one-pager.md`，或直接贴出内容/指定路径，读取并进入审查。

### 2. 对照 5 个核心维度做克制审查

按以下 5 项检查核心是否到位（**抓大放小，不抠无关紧要的细节**）：

1. **背景与问题（Why）**：是否说清要解决什么问题、为什么现在改？
2. **目标与非目标（Scope）**：是否明确“做什么”以及**“明确不做什么”**？
3. **核心方案与关键权衡（What & Trade-off）**：能否一句话讲清方案，并说明**为什么选它、放弃了什么**？
4. **影响范围与风险（Risk）**：是否说清改了什么、影响谁、怎么验证改对了、出了问题怎么兜底/回滚？
5. **需要对方做什么（Call to Action）**：是否明确需要谁拍板、谁配合，还是仅同步知晓？

### 3. 输出精炼反馈

- **先给结论**：明确当前这版能不能直接发给团队看（可发送 / 需补充关键信息后再发）。
- **只问关键问题**：仅针对真正影响理解或有明显漏洞的地方追问，不为了“凑齐五项的字数”而强行挑刺。
- **剔除空话**：若出现“全面提升稳定性”“优化架构”等空泛表述，提示换成具体可感知的动作或结果。

### 4. 到位即止

- 开发者补充后，只要核心逻辑通顺、关键风险与边界已交代清楚、**给人能看懂**，就明确告知“可以发了”，停止继续追问。
