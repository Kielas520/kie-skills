# 推送前的本地测试

按工单要求把改动测到位，再把结果写成测试报告。本技能只做测试与报告，不改业务实现，也不执行提交与推送。

## 前置条件

- 当前在本次任务的分支与工作区内（分支由 `kie-git-worktree` 建立）。
- 实现已经完成，`kie-dev-execute` 的计划任务全部勾选。
- 有工单时先取到工单内容与验收标准。工单信息由用户给出，或从用户提供的单号与工单链接读取；取不到就问用户要，不靠猜。

## 测试范围

动手之前先说明这次测什么：覆盖哪些验收标准、涉及哪些产物、怎么验证。测完把同一份说明写进报告。

| 情况 | 做法 |
| --- | --- |
| 有工单 | 按工单内容与验收标准测，改动影响的本地产物全部测一遍 |
| 无工单 | 至少验证分支的功能是否正常，或缺陷是否已经解决 |

### 有工单

1. 逐条列出工单的验收标准，标出每条对应的产物与验证方式。
2. 把改动影响的产物在本机构建出来，逐个过验收标准。
3. 缺陷单按下一节做对照实验。
4. 工单里写的复现步骤、边界条件、异常输入实际跑一遍；工单没写但改动涉及到的路径一并验证。

### 无工单

- 自己列验证项：新功能走主要路径与边界，缺陷修复按报告里的复现步骤重跑。
- 验证项与结论照样写进测试报告，报告里写明这次没有关联工单。

## 缺陷单的对照实验

缺陷修复必须有有问题版本与当前分支的对照结果，只有当前分支的现象不足以说明问题已经解决。

1. 从工单里找出问题发生时使用的版本：tag、commit、安装包、固件版本，记录下来。
2. 取那个版本的产物或源码，按工单描述的环境与步骤复现，确认问题确实出现。环境尽量与工单对齐（系统版本、依赖版本、硬件、配置），对不齐的部分在报告里写明差异。
3. 用当前分支的构建产物跑同样的步骤，确认问题不再出现。
4. 两边的现象与输出都记进报告的对照实验段。

复现不出问题时按实际现象汇报：把当前现象、环境差异与可能的原因写进报告，交用户判断，不写成「没有问题」。

## 语言层面的规则

构建、静态检查、测试集选择按项目约定执行，语言专属规则读对应技能：

| 语言 | 技能 | 内容 |
| --- | --- | --- |
| Rust | `kie-rust-gates` | 改动范围判定、fmt 与 clippy、受影响测试集选择 |
| Python | `kie-python-style` | 环境与依赖管理、写法约定 |

工单驱动的内容验收归本技能，语言的机械门禁归上面两个技能，两者都要过。

## 测试报告

测试通过、用户确认可以推送之后再写报告，写到 `~/project/<项目名称>/.idea/test-report.md`，结构按 [assets/测试报告模板.md](assets/测试报告模板.md)。项目名以用户给的为准，用户没说就按当前工作目录的仓库名。

- 报告固定这一份文件，新一轮测试覆盖写最新结果，不留旧版本。
- 测试结果写成表格，逐条对应验收标准，写清预期与实际。
- 缺陷单的对照实验单独成段，两张版本的结果并列。
- 没测到的部分写进「未覆盖」，说明原因与影响。
- 远端 CI 结果段在本地测试阶段留空，由 `kie-pr-ci-test` 追加。

用户确认报告内容之后，它同时作为 `kie-pr-start` 起草 PR body 的测试报告来源。

## 交付

```text
━━━ 本地测试完成 ━━━
工单: {m-/f- 单号，无工单省略本行}
范围: {测了哪些产物、哪些验收标准}
对照实验: {缺陷单写明有问题版本与当前分支的结果，无则省略本行}
报告: ~/project/<项目名称>/.idea/test-report.md
未覆盖: {没测到的部分，没有则省略本行}
下一步: 用户确认后推送并发起 PR，PR body 起草走 kie-pr-start
```

## 硬性约束

- 不擅自提交与推送：`git add`、`commit`、`push` 只在用户明确要求时执行。
- 不用 mock、伪造输出或放宽验证项的方式凑结果。
- 测不出结论时按事实汇报，不宣称已经通过。

## Gotchas

- 「能编译」「单测过了」不等于工单验收完成。验收标准要落到实际产物与可观察的输出上。
- 用户可能在本轮测试期间改动代码，动手前重读改动范围，基于当前内容测。
- 报告在用户确认可以推送之后才写。提前写完再被改动推翻，报告就失效了。
- 本地测试与 PR 的远端 CI 测试是两次独立验收，本地通过不代表远端产物通过。
- 工单的验收标准往往不止一条，漏测的那条要写进「未覆盖」并说明影响，不能只测主路径。
- 无工单的分支也要测，不能因为「没有验收标准」跳过测试直接推送。
