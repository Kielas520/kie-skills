# 推送前的本地测试

按工单要求把改动测到位，再把结果写成测试报告。本技能只做测试与报告，不改业务实现。`<项目名称>` 与 `<任务>` 的取值、文档目录与中间结果的落点见 `kie-agent-rules` 技能目录下的 `references/workspace.md`。

## 子能力

| 子能力 | 产出 | 何时做 |
| --- | --- | --- |
| 说明测试范围 | 这次测哪些验收标准、哪些产物、怎么验证 | 用户要求测试时 |
| 执行测试 | 每条验收标准的实际结果；缺陷单的对照实验结果 | 用户确认测试范围后 |
| 写测试报告 | `.idea/<任务>/test-report.md` | 测试通过、用户确认可以推送之后 |

测试范围说明完后停下来，用户确认后才开始测。

## 测试依据

- 工单的内容与验收标准：由用户给出，或从用户提供的单号与工单链接读取；取不到就问用户要，不靠猜。用户说明没有工单时，按「无工单」测。
- 改动范围：当前分支相对 main 的累计改动，加上工作区里未提交的改动。用户可能在测试期间改动代码，动手前按当前内容重新确定范围。

## 说明测试范围

| 情况 | 范围 |
| --- | --- |
| 有工单 | 逐条列出工单的验收标准，标出每条对应的产物与验证方式；工单里写的复现步骤、边界条件、异常输入都列进去；工单没写但改动涉及到的路径一并列出 |
| 无工单 | 自己列验证项：新功能走主要路径与边界，缺陷修复按问题描述里的复现步骤重跑 |

同时说明有没有真实设备（见下一节）、缺陷单要用哪个有问题版本做对照。

## 真实设备

测试前先检索有没有可用的真实设备，检索方式按项目 `AGENTS.md` 写的来，没写就问用户。

- 有真实设备：涉及设备的验收标准必须在真机上测。
- 没有真实设备：可以用 mock 代替，在报告的「测试环境」与「未覆盖」里写明真机没有测、影响是什么。

## 执行测试

1. 把改动影响的产物在本机构建出来，逐个过验收标准。构建与测试只取改动涉及的最小范围（改动的包、构建目标、用例），复用工作区已有的构建产物，不执行推送前的整仓门禁。
2. 缺陷单按下面的步骤做对照实验。

缺陷修复必须有有问题版本与当前分支的对照结果，只有当前分支的现象不足以说明问题已经解决：

1. 从工单里找出问题发生时使用的版本：tag、commit、安装包、固件版本，记录下来。
2. 取那个版本的产物或源码，按工单描述的环境与步骤复现，确认问题确实出现。环境尽量与工单对齐（系统版本、依赖版本、硬件、配置），对不齐的部分记下来。
3. 用当前分支的构建产物跑同样的步骤，确认问题不再出现。

复现不出问题时按实际现象汇报：把当前现象、环境差异与可能的原因交用户判断，不写成「没有问题」。

## 写测试报告

测试通过、用户确认可以推送之后，按 [assets/测试报告模板.md](assets/测试报告模板.md) 的模板与「填写要求」写到 `~/kie-ws/<项目名称>-p/.idea/<任务>/test-report.md`，任务目录不存在就创建。

交付格式：

```text
━━━ 本地测试完成 ━━━
工单: {m-/f- 单号，无工单省略本行}
范围: {测了哪些产物、哪些验收标准}
对照实验: {缺陷单写明有问题版本与当前分支的结果，无则省略本行}
报告: ~/kie-ws/<项目名称>-p/.idea/<任务>/test-report.md
未覆盖: {没测到的部分，没有则省略本行}
```

## 硬性约束

- 不用伪造输出、放宽验证项的方式凑结果。

## Gotchas

- 「能编译」「单测过了」不等于工单验收完成，验收标准要落到实际产物与可观察的输出上。
- 本地测试与 PR 的远端 CI 测试是两次独立验收，本地通过不代表远端产物通过。
