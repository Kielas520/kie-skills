# 开发与测试

以用户确认的 `design.md` 为依据实现，并按其中的验收内容测试。每项工作目录位于 `~/kie-ws/<仓库名>/<name>/`，分支代码位于其下的 `branch_source/` 或工单号目录。用户指定其他依据或位置时使用指定位置。

## 子能力

| 子能力 | 产出 |
| --- | --- |
| 开发 | 实现代码、配套测试和实现过程中的验证结果 |
| 测试 | 设计验收项的实际结果与 `.tmp/test-n/test-report-n.md`，必要时含缺陷对照和 CI 产物结果 |

分别按用户本次授权执行子能力；完成已授权的开发后，若用户尚未授权测试，报告开发结果并等待授权。用户已同时要求开发和验收时，完成开发后继续测试，不额外要求一般性范围确认。涉及外部环境或设备的最终验收遵守下文的设备确认规则。

## 依据与落点

在本项工作目录查找 `design.md`，读取完整设计及其验收内容；找不到、内容不足或设计尚未确认时，向用户询问依据或缺失内容，取得依据前不臆造实现或验收标准。动手前重新读取相关章节。实现与设计冲突或缺少实现必需的决定时，说明具体问题并等用户决定。

每项工作独立编号：每次测试检查该工作目录 `.tmp/` 中已有的 `test-n/`，取已有最大编号加一，从 1 开始；创建 `.tmp/test-n/`，测试文件、下载的测试产物及报告均放在本次目录，报告名为 `test-report-n.md`，编号与目录一致。既有测试目录和报告保留。与测试无关的临时文档放在 `.tmp/docs/`。

## 开发

按设计完成所有受影响的代码、调用方及配套测试，遵循仓库已有约定。对行为改动编写并运行针对性的测试，实际运行改动路径，检查真实输出；检查与构建选择受影响的最小范围，复用现有产物。失败时根据完整错误定位并修复，不通过削弱断言或跳过检查掩盖失败。

编写任何 Python 测试脚本前，先读取 `kie-python-style` 技能并遵循其中约定；技能不可用时停止编写该脚本，询问用户如何获取，不自行替代。开发中自行验证的测试结果用于实现闭环，不作为最终验收报告的内容。

## 测试

逐条依据 `design.md` 中的验收内容确定测试对象、预期和验证方式，实际运行对应产物，记录真实结果、证据与未覆盖项。测试失败时如实记录，按用户授权处理；不以构建成功、单元测试通过或 CI 绿灯替代验收，也不以模拟结果冒充真实设备验收。缺陷修复在依据提供有问题版本及复现条件时，用同一操作对照有问题版本与当前产物，记录版本、环境差异和现象；无法复现或缺少条件时如实记录并向用户询问。

编写 Python 测试脚本前同样必须先读取 `kie-python-style`；不可用时停止编写并询问用户。测试完成后，无论通过、失败或存在未覆盖项，按 [测试报告模板](assets/测试报告模板.md) 写本轮报告。报告逐条对应设计验收内容，只写最终验收测试，不写开发过程中自行验证的测试。

### 外部环境与设备

最终验收涉及本机不存在的环境或需要额外设备时，先检查本项工作目录的 `devices.md` 并读取其内容，再向用户确认是否开始执行。文件不存在或内容不足时，询问用户是否继续以及如何提供环境、设备和执行测试；未得到明确答复前，不执行需要该环境或设备的验收。已确认设备与执行方式后才开始相关测试；无法执行的验收项如实标为未覆盖及说明影响，不以模拟测试宣称通过。

### CI 产物

用户要求验收 PR 的 CI 产物时，检查对应 PR 的 CI 状态，等待运行结束；检查失败或取消时说明结果与链接，让用户决定是否继续。按 [CI 命令参考](references/gh-ci.md) 定位并下载产物到本次测试目录，逐条在实际产物上验证设计验收内容，记录运行及产物链接。缺陷对照和外部设备要求与本地验收相同。产物无法运行时记录缺少的条件，不把 CI 状态当作验收结果。测试报告记录本次远端结果。

用户另行要求 PR 验收评论或更新正文时，以本轮报告起草评论和正文的验证段，保留正文已有内容；评论包括验收结论、CI 产物链接和缺陷对照版本。先交用户确认具体内容，确认后才发布评论或更新 PR 正文；命令见 CI 命令参考。草稿放在本次测试目录。

## 交付

说明开发或测试实际完成的范围，提供本轮报告路径、各验收项结论和未覆盖项及原因；涉及 CI 时附运行与产物链接。未执行的检查和未满足的前提如实说明。
