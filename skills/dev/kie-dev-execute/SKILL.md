# 按设计文档实现

按用户确认的设计文档生成实现计划，计划批准后逐条实现并验证到可运行状态。本技能不改 `design.md`。`<项目名称>` 与 `<任务>` 的取值、文档目录与临时脚本的落点见 `kie-agent-rules` 技能目录下的 `references/workspace.md`。

## 子能力

| 子能力 | 产出 | 何时做 |
| --- | --- | --- |
| 生成计划 | `.idea/<任务>/plan.md` | 用户要求按设计文档开始实现时 |
| 逐条实现 | 代码改动，`plan.md` 里的勾选 | 用户批准计划后 |
| 整体验证 | 改动相关检查的结果与实际运行结果 | 计划任务全部勾选后 |

计划写完后停下来，把 `plan.md` 路径与任务清单给用户，用户批准后才开始实现。

## 实现依据

在同一任务目录 `.idea/<任务>/` 下找 `design.md`。找不到，或用户还没确认这份设计时，问用户实现依据在哪里，依据到手之前不生成计划、不改代码。

动手前重读 `design.md` 的受影响章节，用户可能在开发过程中改过它。

## 生成计划

读 `design.md` 全文，按 [assets/plan.md](assets/plan.md) 的模板与「填写要求」写 `~/kie-ws/<项目名称>-p/.idea/<任务>/plan.md`。

## 逐条实现

对每个未勾选任务：

1. 属于新增或修改行为的改动，先写测试并运行，看它失败。
2. 实现到测试通过。
3. 运行该任务的验收命令，看真实输出。复用工作区已有的构建产物，靠增量编译推进，不为了验证整仓重新构建。
4. 验收通过，把 `- [ ]` 改成 `- [x]`，进入下一个任务。

仓库没有测试框架时，用最小可运行脚本或实际调用验证改动路径，脚本放在中间结果的落点，验证完删除（进回收站）。

命令或测试失败：读完整错误输出定位根因再改，不注释测试、不放宽断言、不跳过验收命令。

遇到下面两种情况，暂停当前任务，把设计写的是什么、实际遇到了什么告诉用户，等用户决定：

- 实现与设计不符：设计里的签名不可行、依赖不存在、环境不具备。
- 设计漏写了必须一起改的地方。用户决定补进计划后，才把它加进 `plan.md` 再执行。

后一个任务的前置还没做时，调整顺序并在 `plan.md` 里改过来，不硬按原顺序执行。用户撤回已完成的改动时，把对应任务改回未勾选。

## 整体验证

全部任务勾选后：

1. 找与本次改动相关的检查：读项目 `AGENTS.md`、`CLAUDE.md`、`README.md`、CI 配置（`.github/workflows/`）、`Makefile`、`scripts/` 下的检查脚本，挑出改动涉及的构建、测试、lint、格式、文档项执行。命令同样取改动涉及的最小范围；整仓全量测试与推送前门禁不在这一步跑，语言门禁见对应的语言技能。
2. 实际运行改变的功能：CLI 与脚本直接执行看输出，服务类启动后打真实请求，UI 用浏览器打开看界面，库类写临时脚本调用改动路径。观察到真实结果才算验证，不把验证交给用户。
3. 无法在本机运行的场景（需要真实设备、外部服务）：说明缺什么前提，把已完成的验证范围写清楚。

本技能的运行验证只覆盖实现闭环，不替代按工单验收标准做的验收测试。

汇报格式：

```text
━━━ 实现完成 ━━━
计划: ~/kie-ws/<项目名称>-p/.idea/<任务>/plan.md（<n> 个任务全部勾选）
整体验证: <命令> 通过 / <命令> 通过
运行验证: <运行了什么、看到什么>
遗留: <未覆盖的问题，没有就省略本行>
```

## Gotchas

- `plan.md` 的勾选是进度记录，完成与否以验收命令的真实输出为准，不接受「应该能过」的判断。
- `.idea/` 在项目容器里，不在仓库内，也不参与版本控制，`plan.md` 的历史段不依赖 git 找回。
