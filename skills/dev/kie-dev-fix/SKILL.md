# 处理评审意见

根据 PR 评论或用户指定的评审文件判断问题并记录修复方案；意见是否采纳由用户决定。发送评论由 `kie-commit-pr` 负责。

## 子能力

| 子能力 | 产出 |
| --- | --- |
| 分析评审意见 | `<工作目录>/.tmp/fix/fix-n.md`，包含问题、状态、方案和验收方式 |
| 修复问题 | 按用户确认的方案修改代码并记录结果 |

`<工作目录>` 是 `~/kie-ws/<仓库名>/<name>/`，分支代码位于其下的 `branch_source/` 或工单编号目录。`n` 在当前工作的 `.tmp/fix/` 中递增，与其他工作互不影响。

## 分析与记录

1. 用户指定 `comment-review-n.md` 时读取该文件及其对应代码，不要求 PR。否则确定 PR 仓库与编号，拉取未解决的 review threads、review body 和会话区 issue comments，命令见 [references/github-pr-review.md](references/github-pr-review.md)。无法确定来源时询问用户。
2. 结合当前实现逐条判断意见是否成立、是否已解决，记录来源、具体位置和理由；需要解决的问题写出方案、影响范围与验收方式。不得仅凭评论声称采纳。
3. 每次执行前检查当前工作的全部 `.tmp/fix/fix-n.md`，按问题的来源、位置和实质内容识别已有问题；来源不同但实质相同也要关联。无法判断是否同一问题时询问用户。
4. 新问题写入新文档，编号取已有 fix 文档最大编号加一；没有文件时从 1 开始。已有问题继续更新其原文档，将该文档重命名为当前最大编号加一，并同步修改文档内部编号及当前工作范围内指向旧文件名、路径或文档编号的已有引用，保留历史记录。多个已有文档依次分配不同的新编号；新旧问题混合时，新问题仍写入独立新文档，所有编号依次递增且不得覆盖。若某引用无法安全更新，先告知用户并停止迁移，不留下失效引用。
5. 按 [assets/fix.md](assets/fix.md) 填写同一份 fix 文档，不另写审核文档。把文档路径与方案交给用户；用户反馈方案有问题时直接修改该文档，直到用户确认。

## 修复

用户授权实现后按确认的方案修改代码，并按本次授权进行验证，将每项结果与未解决事项更新到对应 fix 文档。需要反馈 PR 评论时，按本次授权准备回复内容；不得自行发送评论或修改 PR body。
