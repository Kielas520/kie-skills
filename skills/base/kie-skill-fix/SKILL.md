# 技能修复

某个已装技能的行为跟它自己的定位对不上时，从现象查到根因，改完把现象固化成回归用例。本技能不动代码、不处理 PR 评审意见，也不新建技能。

## 与 kie-skill-dev 的分工

frontmatter 与正文的写法、`skills-ref` 校验、软链接接入、评估脚本与用例 schema、总结确认、提交部署，按 `skill://kie-skill-dev` 的第 2 至 5 步与第 6 至 9 步执行。本文件只写开发流程里没有的那一段：从现象查到根因，再出修复方案与回归用例。

## 前置条件

- 反馈的对象是技能的行为。属于代码缺陷、PR 评审意见或文档写作的，按 description 里的对照表转走。
- 能确认是哪个技能：用户给了技能名、技能目录，或某次会话里的表现。确认不了先问用户，不靠猜。
- 复现跑评估沙箱，脚本在 `~/kie-ws/kie-skills/skills/base/kie-skill-dev/scripts/` 下，只在 kie-skills 仓库内可用。沙箱位置与内容来源边界按 kie-skill-dev 的「调查边界」段。
- 用哪个 agent CLI 跑评估由用户定，先 `--list-agents` 看本机有哪些，再问用户。

## 步骤

### 1. 把现象落成三行

| 项 | 写什么 |
| --- | --- |
| 现象 | 用户看到的：哪句话触发、技能做了或没做什么 |
| 实际行为 | 技能当时实际做了什么 |
| 期望行为 | 按它的 description 与正文，它本该做什么 |

用户的原话保留在方案里。

### 2. 复现

触发类现象（老是不触发、误触发）与行为类现象（越界、做错事、输出走样）复现方式不同：

- 触发类：把用户当时那句话写进 `.scratch/` 下的临时查询文件，用 `--queries` 指定它跑单条：

  `python3 ~/kie-ws/kie-skills/skills/base/kie-skill-dev/scripts/trigger_eval.py <技能名> --agent <名字> --queries .scratch/<文件>.json --runs 1`

- 行为类：把当时的输入压成一条用例，临时加进被改技能的 `evals/evals.json`，用 `--cases <id>` 只跑这一条，看带技能组的产物里有没有那个错误行为。这条用例就是第 6 步要留下的回归用例。

复现只在本次会话内做完：单条用例、跑一轮，不铺开多批。复现不出来时，把三行现象、已经排除的假设与当前实际现象一起汇报给用户判断，不写成「没有问题」，也不靠猜改文件，更不要把复现交给后台任务后收尾等结果。

### 3. 归类根因

| 根因 | 表现 | 改哪里 |
| --- | --- | --- |
| description 覆盖不足 | 该触发时不触发 | 按 kie-skill-dev 第 2 步重写四块 |
| description 反例排除缺失 | 越界、误触发 | 不适用清单里补上那条边界 |
| 正文缺规则 | 该做没做 | 把期望行为写成一条可执行的规则 |
| 正文规则之间相互冲突 | 做错事 | 以正确的那条为准，删掉冲突的写法 |
| 正文太笼统 | 输出走样 | 换成真实命令、具体步骤与判断条件 |
| 用例本身写错 | 看着像 bug，技能其实没问题 | 修用例，不动技能 |
| 软链接缺失或名字不一致 | 技能装不上、加载不到 | 按 kie-skill-dev 第 5 步重建链接 |

description 的四块指做什么、何时用、边界、反例排除。

### 4. 出修复方案等批准

方案里写清：根因归到哪一类、改哪个技能、动 description 还是正文哪一段、改完的预期行为、复现方式与用例、`metadata.version` 怎么走、补哪条回归用例、跑第 7 步还是第 8 步。用户请求里的「帮我修一下」不算对方案的批准：方案发出后停在会话里等回应，没回应就不动文件。第 2 步为复现临时加的用例不算改动。

### 5. 改完验证

批准后按方案改，改完按 kie-skill-dev 第 6 步总结等用户确认，再跑评估：description 动过必须跑第 7 步（正例与负例都跑），正文动过跑第 8 步，两者都动就都跑。

### 6. 留下回归用例

- 触发类：把第 2 步的临时查询并进被改技能的 `evals/trigger-queries.json`，字段按官方 schema。
- 行为类：第 2 步加进 `evals/evals.json` 的那条用例补上 `assertions`，断言直接判这次的错误行为，不写「输出合理」这类判不出来的句子。
- 用例要能在沙箱里独立跑通：输入文件按 `evals/files/` 之后的相对路径放好，查询里提到的路径是沙箱里成立的说法。

## 硬性约束

- 用户批准方案之前不改技能内容文件；请求里的「帮我修一下」不算批准。
- 不为了通过评估而放宽断言、删用例，或改用户给的期望。
- 复现不出、根因不在技能本身、或者修不掉时按事实汇报。

## Gotchas

- 用户报的现象常是根因的下游表现。「这个技能越界了」的根因可能在 description 的反例排除，也可能在正文缺约束，别停在第一层。
- 越界与不触发是相反的改动方向：description 补完边界要把正例与负例一起重跑，往不适用清单里补场景有时反而会把那条场景吸引过来。
- 负例的单轮结果会在 0 与 1 之间翻，判定负例用 `--runs 3` 的累计触发率，别拿一轮的 0 或 1 当回归。
- `description` 有 1024 字符上限，补边界时容易超，改完核一遍。
- 用户对技能写法的评价与建议属于讨论，只回答、不写文件；给出开工指令后才按方案改。
- 没有回归用例的修复下次会原样复发，第 6 步不能省。
