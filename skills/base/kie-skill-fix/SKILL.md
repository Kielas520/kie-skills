# 技能修复

某个已装技能的行为跟它自己的定位对不上时，从现象查到根因，改完把现象固化成回归用例。本技能不动业务代码、不处理 PR 评审意见，也不新建技能。

## 子能力

| 子能力 | 产出 | 改不改技能文件 |
| --- | --- | --- |
| 复现与定根因 | 三行现象、复现结论、根因归类 | 不改，复现用例放在 `.scratch/` |
| 修复方案 | 改哪里、怎么改、预期行为、版本号、回归用例 | 不改 |
| 实施修复 | 改好的技能文件、更新日志、回归用例 | 改，方案批准后才动 |

请求里的「帮我修一下」只授权复现与出方案，不算对方案的批准：方案发出后停在会话里等回应，没回应就不动技能文件。

frontmatter 与正文的写法、校验、评估、总结确认、更新日志、提交部署，都按 kie-skill-dev 对应的步骤执行（「写 frontmatter」「写正文」「校验」「确认与总结」「触发评估」「输出质量评估」「提交与部署」），沙箱的位置与收尾清理按它的「调查边界」。本文件只写开发流程里没有的那一段。

## 前置条件

- 反馈的对象是技能的行为。属于代码缺陷、PR 评审意见或文档写作的，按 description 里的「不适用」转走。
- 能确认是哪个技能：用户给了技能名、技能目录，或某次会话里的表现。确认不了先问用户，不靠猜。
- 复现用的评估脚本在 `~/kie-ws/kie-skills/skills/base/kie-skill-dev/scripts/` 下，只在 kie-skills 仓库内可用。用哪个 agent CLI 跑由用户定，先 `--list-agents` 看本机有哪些，再问用户。

## 步骤

### 1. 把现象写成三行

| 项 | 写什么 |
| --- | --- |
| 现象 | 用户看到的：哪句话触发、技能做了或没做什么 |
| 实际行为 | 技能当时实际做了什么 |
| 期望行为 | 按它的 description 与正文，它本该做什么 |

用户的原话保留在方案里。

### 2. 复现

复现用例只放在仓库的 `.scratch/` 下，不写进被修技能的 `evals/`。

- 触发类（老是不触发、误触发）：把用户当时那句话写进 `.scratch/<任务>/queries.json`，单条跑：

  ```bash
  python3 ~/kie-ws/kie-skills/skills/base/kie-skill-dev/scripts/trigger_eval.py <技能名> --agent <名字> --queries .scratch/<任务>/queries.json --runs 1
  ```

- 行为类（越界、做错事、输出走样）：把当时的输入压成一条用例，写进 `.scratch/<任务>/evals/evals.json`，输入文件放在 `.scratch/<任务>/evals/files/` 下，布局与技能目录的 `evals/` 一致，单条跑：

  ```bash
  python3 ~/kie-ws/kie-skills/skills/base/kie-skill-dev/scripts/quality_eval.py <技能名> --agent <名字> --evals-root .scratch/<任务> --cases <id> --no-grade
  ```

  看带技能组的产物里有没有那个错误行为。

复现在本次会话里跑完一轮、拿到结果再汇报，不铺开多批。复现不出来时，把三行现象、已经排除的假设与当前实际现象一起汇报给用户判断，不写成「没有问题」，也不靠猜改文件。

### 3. 归类根因

| 根因 | 表现 | 改哪里 |
| --- | --- | --- |
| description 覆盖不足 | 该触发时不触发 | 按 kie-skill-dev「写 frontmatter」重写 description |
| description 反例排除缺失 | 越界、误触发 | 不适用清单里补上那条边界 |
| 正文缺规则 | 该做没做 | 把期望行为写成一条可执行的规则 |
| 正文规则之间相互冲突 | 做错事 | 以正确的那条为准，删掉冲突的写法 |
| 正文太笼统 | 输出走样 | 换成真实命令、具体步骤与判断条件 |
| 用例本身写错 | 看着像 bug，技能其实没问题 | 修用例，不动技能 |
| 名字不一致 | 技能加载不到 | 按 kie-skill-dev 的改名 Gotcha 逐处核对目录名、`name` 与引用 |

### 4. 出修复方案

方案里写清：三行现象与复现结论、根因归到哪一类、改哪个技能、动 description 还是正文哪一段、改完的预期行为、`metadata.version` 怎么走、回归用例怎么留、改完跑触发评估还是输出质量评估。发出后等用户批准。

### 5. 实施修复

批准后按方案改，按 kie-skill-dev「确认与总结」总结等用户确认，再跑评估：description 动过跑触发评估（正例与负例都跑），正文动过跑输出质量评估，两者都动就都跑。改动与它的更新日志同批写。

### 6. 留下回归用例

- 触发类：把第 2 步 `.scratch/` 里的查询并进被修技能的 `evals/trigger-queries.json`。
- 行为类：把第 2 步 `.scratch/` 里的用例与输入文件并进被修技能的 `evals/evals.json` 与 `evals/files/`，补上 `assertions`。断言直接判这次的错误行为，不写「输出合理」这类判不出来的句子。
- 用例要能在沙箱里独立跑通：输入文件按 `evals/files/` 之后的相对路径放好，查询里提到的路径是沙箱里成立的说法。

## 硬性约束

- 不为了通过评估而放宽断言、删用例，或改用户给的期望。
- 复现不出、根因不在技能本身、或者修不掉时按事实汇报。

## Gotchas

- 用户报的现象常是根因的下游表现。「这个技能越界了」的根因可能在 description 的反例排除，也可能在正文缺约束，别停在第一层。
- 没有回归用例的修复下次会原样复发，第 6 步不能省。
