# 发布记录这套东西现在怎么做的（wuji-cli-dev）

## 背景

- 项目：wuji-cli-dev，Rust 写的设备命令行工具，发布记录写在仓库根的 `CHANGELOG.md`。
- 同一份内容给两拨人看：对外用户，和发版前先在飞书群里同步的内部同事。
- 谁写：当次发版的人自己写，一般是负责这个版本的开发。

## 现在实际怎么取信息

1. 上一个 tag：`git describe --tags --abbrev=0 <本次tag>`
2. 区间内的合并提交：`git log <上一个tag>..<本次tag> --merges --pretty='%h %s'`
3. 区间内的非合并提交：`git log <上一个tag>..<本次tag> --no-merges --pretty='%h %s'`
4. 要看细节时打开对应的 PR：`gh pr view <编号> --json title,body`
5. 关联的飞书单号藏在提交信息里，形如 `f-7128574383`，用 `git log <上一个tag>..<本次tag> --grep='f-'` 抓

## CHANGELOG.md 里已有的写法

- 版本节标题带日期：`## 0.9.3（2026-10-08）`
- 分节固定三类：`新增`、`修复`、`变更`；某一类没有内容就把整节删掉，不写「无」
- 每条一句话，动词开头，把 `fix: parse crash on empty frame` 这类提交标题改写成中文短句「修复空帧导致的解析崩溃」
- 破坏性变更单独一节 `### 破坏性变更`，位置在`变更`之上
- 不贴内部链接，只留飞书单号

## 判断条件（踩过的坑）

- 只有依赖升级、没有用户可见行为变化的版本，三类都可能是空的，这时写一句「本版本仅依赖升级，无用户可见变化」
- 补发的热修版本（例如 `0.9.3.1`）合并进它对应的主版本那一节，不新开一级标题
- 预发布版本（`-rc.1`）不进 `CHANGELOG.md`，只在飞书群发
- 同一个 PR 里既有功能又有修复时，按改动大的那一类归，不重复列
- 一个版本里同一个模块的改动超过五条时，按模块合成一条，细节留在 PR 里

## 不写什么

- 不写重构、测试、CI、文档修改
- 不写依赖版本号清单，不贴 diff
- 不用「若干」「一些」这类含糊说法
