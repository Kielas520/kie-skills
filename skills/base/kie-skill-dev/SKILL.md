# 技能开发

个人技能仓库里 Agent Skill 的创建、修改与验证。

Agent Skills 的格式约束不写死在本文件里：字段、目录约定、评估 schema 一律实时从 `https://agentskills.io/llms.txt` 及其页面拉取。本文件是工作流。规则优先级：以下仓库约定 > 官方文档 > 本文件其余内容。

改动技能之后按改的内容选评估：`description` 动过走第 7 步触发评估，正文动过走第 8 步输出质量评估。用户报某个已装技能出现行为异常（越界、该做没做、做错事、输出走样、不触发或误触发）时走 kie-skill-fix。

## 调查边界

技能内容的来源只有用户给的输入，以及本仓库与 `~/project/AGENTS.md` 引用范围内的约定。

- 允许读取：本仓库内的文件、用户显式提供的文件与链接、`~/project/AGENTS.md` 及其明确引用的开发约定。
- 不作为技能内容依据：`~/.agents/skills/` 等用户层技能目录、`~/.omp/` 与 `~/.claude/` 等 agent 运行时配置、其他仓库的技能与参考文件。
- 评估沙箱建在 `~/project/test/coop-<沙箱标记>/` 下（目录名由技能名哈希得到，不含技能名），仓库内只保留 `.scratch/` 里的运行结果。
- 用户给的输入明确指向某个外部技能时，才读取该技能，并在产出里说明来源。

## 仓库约定

| 约定 | 内容 |
| --- | --- |
| 位置 | `skills/<分类>/<技能名>/SKILL.md` |
| 命名 | 目录名等于 frontmatter `name`，统一 `kie-` 前缀，只用小写字母、数字、连字符 |
| 分类 | 只用于组织源文件，按领域划分（`base/` 元技能与协作规则，其他按实际需要新增） |
| 版本 | `metadata.version` 用 semver，新技能从 `0.1.0` 起。影响 agent 行为的改动（description、规则、compatibility）bump minor，纯文字与格式修正 bump patch |
| 评估 | 每个技能带 `evals/trigger-queries.json`（触发，官方 schema）与 `evals/evals.json`（输出质量，官方 schema）。评估依据只来自用户输入与本仓库，用户层技能与其他仓库的参考文件不作为依据 |
| Gotchas | 正文保留 `## Gotchas` 段，用户每次纠正技能行为后把结论写回该段或对应步骤 |

## 流程

### 1. 拉取官方文档

先读 `https://agentskills.io/llms.txt` 取页面索引，再按任务拉取需要的页面：

| 任务 | 页面 |
| --- | --- |
| 字段、目录结构、渐进式披露 | `specification.md` |
| 第一次做、最小示例 | `skill-creation/quickstart.md` |
| 内容设计、控制力度、Gotchas、输出模板 | `skill-creation/best-practices.md` |
| 触发准确性 | `skill-creation/optimizing-descriptions.md` |
| 输出质量评估 | `skill-creation/evaluating-skills.md` |
| 打包可执行脚本 | `skill-creation/using-scripts.md` |

页面名以第 1 步索引里的当前列表为准。新建技能至少拉取 `specification.md` 与 `skill-creation/best-practices.md`，改动已有技能至少拉取 `specification.md`。不凭记忆写字段与约束。

### 2. 写 frontmatter

- `name` 与父目录名一致，1 至 64 字符，只能包含小写字母、数字、连字符，首尾不能是连字符，不能出现连续连字符。
- `description` 覆盖四块内容：做什么、何时用（含用户不会明说的场景）、边界、反例排除。不复述执行步骤，复述会让 agent 按 description 行事而不读正文。上限 1024 字符。
- 有明确环境依赖时写 `compatibility`，1 至 500 字符。
- `metadata` 用字符串键值对，写 `author` 与 `version`。

### 3. 写正文

正文补 agent 不知道的东西：仓库约定、真实命令、踩过的坑、决策条件。前置条件、步骤、输出要求、验证方法按任务组织。正文控制在 500 行内，超出的细节移进 `references/`，正文写清何时读取。

技能内容来自真实执行过程：做过的任务顺序、用户的纠正、实际命令与输出格式。通用建议不进技能。

### 4. 校验

```bash
uvx --from skills-ref agentskills validate skills/<分类>/<技能名>
```

输出 `Valid skill: <目录>` 即通过。校验器只检查 frontmatter 与命名约束，内容质量由第 7 步与第 8 步的评估判定。

### 5. 本地接入

技能位于分类目录下，技能发现只看技能根目录下一层，分类层不参与扫描。接入目录按选定的 agent CLI 走，建立链接后仓库内的会话才能读到：

```bash
ln -sfn ../../skills/<分类>/<技能名> .agents/skills/<技能名>   # omp
ln -sfn ../../skills/<分类>/<技能名> .claude/skills/<技能名>   # claude
```

用该 agent 的无头会话确认能读到：

```bash
omp -p --mode json --no-session "读取 skill://<技能名> 的正文" | grep -o '"resolvedPath":"[^"]*"'
claude -p "读取技能 <技能名>" --output-format stream-json --verbose | grep -o '"skill": *"<技能名>"'
```

输出技能目录内的路径说明接入成功；omp 报 `Unknown skill: <技能名>`、claude 没有加载记录，说明链接缺失或名字不一致。

### 6. 确认与总结

进入评估之前先向用户总结这次改动，等用户同意再往下走：改了哪些文件、frontmatter 动了哪些字段、正文加了或改了哪些规则、版本号怎么动、接下来准备跑哪几步评估。

- 提问与改动分开：用户问「行不行」「能不能」这类问题时只回答问题，不动文件；有明确的改动要求之后才写文件。
- 用户提出修改就改完重新总结，不进入评估。
- 用户明确同意开始下一步之后，才启动第 7 步与第 8 步。
- 不代替用户判断「改动很小不用看」。

### 7. 触发评估

改 `description` 必须重跑评估。

用例写在技能的 `evals/trigger-queries.json`，采用官方 schema `[{"query": "...", "should_trigger": true}]`，约 20 条。正例覆盖不同表述：明说与不明说、简短与带上下文、正式与口语。负例取关键词重合但任务不同的近似场景，无关查询测不出边界。查询写成用户真实口吻，但不要求会话碰远端：触发、推送、合并、打 tag、发 release、发通知，以及去 GitHub 取 Actions、PR、Release 的状态都算。写完逐条过一遍，把要会话动手或去远端取状态的查询改成静态请求或信息型提问：

| 要测的情形 | 写成 |
| --- | --- |
| 触发发版 | `wuji-cli-dev 要发 2026.10.8，先别动远端，把要跑的命令和顺序列出来` |
| 合发版 PR | `发版 PR 我看过了，合之前还要核对哪些东西` |
| 跟进 tag 与公开仓 | `合进 main 之后 tag、Release 与公开仓同步是谁来做的，我怎么确认` |

评估会话由某个 agent CLI 驱动，先探测本机有哪些、问用户用哪个，不要默认某一个：

```bash
python3 scripts/trigger_eval.py --list-agents
```

```bash
python3 scripts/trigger_eval.py <技能名> --agent <名字> [--runs 1] [--workers 12] [--cap 60] [--only 3,7]
```

先 `--runs 1` 粗筛正例，负例一律 `--runs 3`：负例的单轮结果经常在 0 与 1 之间翻，只有累计触发率高于 0.5 才算误触发。`--only` 收逗号分隔的序号或查询子串，用来复跑翻转项。

脚本做四件事：

- 在 `~/project/test/coop-<技能名哈希>/` 建沙箱：整份 `skills/` 平铺复制进沙箱并删掉各技能的 `evals/`，`work/` 作为会话工作目录，技能按所选 agent 的目录约定投放（omp 写 `overlay.yml` 的 `customDirectories`，claude 用 `--add-dir` 指向带 `.claude/skills` 的目录）。沙箱目录名不含技能名，会话翻到路径时不会顺着名字判定这是该技能的评测。
- 每次运行套 `unshare -rm`，用 tmpfs 盖住本仓库路径、该 agent 的用户层技能目录，以及测试工作区里本次运行之外的目录，会话读不到真实仓库、用户层技能与旁边的其他沙箱。
- 判定看输出里有没有技能加载信号：omp 是 `"resolvedPath":"<沙箱>/skills/<技能名>/SKILL.md"`，claude 是会话用技能工具加载了该技能（目录列举里出现路径不算）。信号一出现就终止会话：它出现在一次运行的前 5% 时间里，之后是无关工作。负例没有这个信号，要等会话自己停下来，受 `--cap` 约束。
- 累计触发率：正例高于 0.5 通过，负例低于 0.5 通过。每次运行的耗时与判定一起记进 `results.json`，路径为 `.scratch/trigger-eval/<技能名>/<时间戳>/results.json`。

开跑前先用第一条正例做预检，不命中就直接中止、退出码 2：整批全 0 或大量「证据不足」通常来自客户端或账号侧，不是描述不准。运行中每 5 秒往 stderr 打一行心跳（完成数与在跑的用例序号），`--verbose` 每完成一次运行再打一行，`--only` 配 `--verbose` 用来定位卡住的查询。

退出码：0 全部通过，1 有未通过的用例或有证据不足的运行，2 无法开始（选不到 agent CLI、隔离条件不成立、预检失败）。没有产生工具调用事件的运行记为证据不足，不计入分母，但会让整批退出码为 1——客户端整个挂掉时每条查询都变成证据不足，只看通过率会把这种情况读成通过。

前后对比固定同一个 agent CLI 与模型，换 CLI 或换模型分数可能差一倍以上。改完 `description` 后正例与负例都要重跑：往「不适用」里补误触发场景，有时反而会吸引该场景命中。

不过关先改 `description` 再重跑。归纳失败查询代表的概念类别，不要堆查询里的原词：把排除项写成负例查询里的原词，会让这类查询命中得更牢。

### 8. 输出质量评估

改完正文、要验证技能输出质量时用。评估会话在本机跑，跟你的 `gh`、ssh 凭据共用同一台机器，用例必须自带边界：

- 用例的输入与预期产物一律在沙箱内闭环。评估的输入（第 8 步质量用例的 `prompt` 与 `files`、第 7 步触发用例的 `query`）不得要求或诱导会话执行离开本机的操作：GitHub 上的 workflow dispatch、push、建或合 PR、打 tag、发 release、发通知，去远端取 Actions、PR、Release 的状态，以及对生产仓库、生产设备、生产服务的写操作。
- 被测技能本身要驱动远端链路（发版、同步公开仓、发布包）时，用例改成在沙箱内的本地 fixture 上验证（沙箱里建裸仓库当 remote，命令指向它），或换一个不涉及远端的技能做用例。
- 写用例前先审一遍被测技能正文里的每一条远端命令，确认用例不会把它执行到真实远端；真远端验证只做静态检查，留给用户手工跑。

用例写在技能的 `evals/evals.json`，字段按官方 schema，`files` 里的内容按 `evals/files/` 之后的相对路径放进工作目录：

```json
{
  "skill_name": "kie-skill-dev",
  "evals": [
    {
      "id": 1,
      "prompt": "用户会真正输入的一句话",
      "expected_output": "成功的样子，人可读",
      "files": ["evals/files/<目录>/SKILL.md"],
      "assertions": ["能从产物里查证的一条断言", "……"]
    }
  ]
}
```

```bash
python3 scripts/quality_eval.py <技能名> --agent <名字> [--iteration 1] [--workers 4] [--cap 600] [--no-grade]
```

同一提示词跑两组：带技能组的沙箱放整份技能集，不带技能组的沙箱技能目录为空，其余条件一致。会话与评分都走 `--agent` 选定的 agent CLI。结果落在 `.scratch/quality/<技能名>/iteration-<N>/<用例>/<组>/`：`outputs/` 是会话产物，`transcript.jsonl` 是完整输出，`timing.json` 记耗时、token、用量与本次实际加载的技能，`grading.json` 记逐条断言判定与证据；`benchmark.json` 汇总两组的断言通过率与差值。

运行撞到 `--cap` 被截断的组在 `timing.json` 里标 `truncated`，并记进 `benchmark.json` 的 `truncated_runs`：产物可能不完整，这一组的通过率不能当结论，换个上限重跑。有运行没有事件输出、有截断、或有评分失败时退出码为 1。

第一轮先不加 `assertions`，用 `--no-grade` 看产物长什么样，再补断言。断言怎么修：两组都过说明这组断言测不出技能价值，删掉或换掉；两组都不过说明断言写错或用例过难；带技能组过、不带技能组不过说明技能在这里起作用。评分完自己读一遍 `outputs/`，把具体意见写进下一轮要改的地方。

迭代循环：改 `SKILL.md`，按第 6 步总结改动并等用户同意，再用 `--iteration <N+1>` 重跑全部用例，重新评分与汇总，再人工复核。带技能组通过率高于不带技能组、且人工复核没有具体意见时收工。

### 9. 提交与部署

第 7 步与第 8 步的评估流程走完之后才进入本步。有未通过的用例、证据不足的运行或评分失败时，先回报结果与下一轮准备改什么，等用户决定。

提交并推送后，部署用 `npx -y skills add Kielas520/kie-skills -g -y`。

## 可用脚本

- **`scripts/trigger_eval.py`** — 触发评估，第 7 步用。隔离沙箱里逐条查询运行无头会话，按技能加载信号判定触发率，写 `results.json`；带预检与心跳，`--list-agents` 列出本机可驱动的 agent CLI，退出码 0/1/2。
- **`scripts/quality_eval.py`** — 输出质量评估，第 8 步用。带技能与不带技能两组各跑一遍用例，调用评分得到逐条断言判定，汇总 `benchmark.json`；有运行没有事件输出、有截断、或有评分失败时退出码为 1。
- **`scripts/agent_cli.py`** — 两者共用的 agent CLI 适配层。加新 agent 时在 `AGENTS` 里加一个子类，会话命令、技能投放位置、判定信号、输出解析四处都要落地。

脚本从自身路径向上找仓库根，只在 kie-skills 仓库内可用。

## Gotchas

- 用户明确要求两道确认：写完到评估之前、评估到提交之前各一次。缺这两次确认就停住等用户，改动再小也一样，也不代替用户判断「不用看」。
- 询问语气不构成改动授权：句尾是「行不行」「能不能」「要不要」，或整句是「你看看…怎么做的」，都只回答问题、不写任何文件；句首带「要解耦啊」这类意向陈述，也还是提问。等用户明确说出要改再动手。
- 触发评估整批全 0 或出现大量「证据不足」时先怀疑客户端与账号侧，不要先去改 `description`。预检退出码 2 与整批退出码 1 都表示这批结果不可用，先复跑确认。
- 分类层不参与技能发现，全靠接入目录里的符号链接，omp 是 `.agents/skills/`、claude 是 `.claude/skills/`。新增分类时同样要建链接。
- 技能改名要同步目录名、frontmatter `name`、`.agents/skills/` 与 `.claude/skills/` 链接、其他技能里的引用、`evals/` 下的用例。仓库全是文本文件，没有工具兜底，改完逐处核对。
- 触发判定看会话有没有加载沙箱里的技能：omp 看 `skill://<技能名>` 的解析记录，claude 看技能目录被加载。读取只说明查阅过，采纳与否看不出来。
- 负例是关键词重合的近似场景时，会话常会为了确认「这件事归不归它管」而加载本技能。description 要给明确的不适用清单，只写适用范围的正面描述拦不住这类加载。
- 触发评估的查询要写成沙箱里也成立的说法。依赖「这个仓库」这类上下文的查询，测到的是沙箱里缺内容。
- 沙箱要装整份技能集：会话启动要读 `kie-agent-rules`，按 description 找相邻技能也可能落空，两者都会退而加载沙箱里唯一的那一个，负例被全部计成触发。
- 只靠配置加工具白名单挡不住会话读到真实仓库、用户层技能与测试工作区里的其他沙箱，必须套 `unshare -rm` 用 tmpfs 盖住这几处。沙箱自身不能放在仓库里，否则会被同一层 tmpfs 一起盖掉。
- 评估沙箱只遮蔽文件系统：会话仍带着本机的 `gh` 与 ssh 凭据，网络照旧。测试一个驱动远端链路的技能时，用例里的提示词会真的被执行到生产——kie-skill-dev 自身的评估里新建过一个发版技能，它的质量用例直接触发了 org 仓库的集中式发版，产出 release PR 与飞书通知。用例的输入要在沙箱内闭环，远端动作换成沙箱内的本地 fixture。
- 会话查不到题目里提到的「这个技能」时会翻文件系统。测试工作区里留着上一轮或另一个脚本的沙箱时，它会翻进去接着答，正例被记成未触发；遮蔽按本次运行的沙箱之外全盖。
- 评估会话用哪个 agent CLI 由用户定：先 `--list-agents` 探测本机有哪些，再问用户，脚本收到 `--agent` 才跑。用户层技能目录、加载信号、会话参数都随 CLI 变，换 CLI 的分数不能与上一批直接比。
- claude 在本机以 Windows 进程运行，`unshare` 里的 tmpfs 遮蔽对它无效，它读得到真实仓库；判定用沙箱路径，读别处的技能副本不算命中。配置目录在 `C:\` 下，那里的用户层技能目录非空时脚本直接报错退出，先清空再跑。
- claude 的 `--restricted` 能限制文件工具，实测会连沙箱技能一起停掉（技能清单里只剩内置项），不能拿它当隔离手段；技能只能从 `--add-dir` 指向的目录投放。
- claude 的会话会主动在文件系统里翻找，负例常要一两分钟才自己停下来，跑 claude 时把 `--cap` 抬到 120 以上，默认 60 会把正常负例记成证据不足。
- 不要靠调低 `--cap` 让负例跑快：截断运行会把本该触发的正例记成未触发。负例的耗时由会话自己停下来的时间决定。
- 负例看单轮结果会误判：同一批负例换一轮跑，通过的与不通过的会互换。判定负例用 `--runs 3` 的累计触发率，别拿一轮的 0 或 1 当回归。
- 评估材料只来自用户输入与本仓库。用户层技能目录与运行时配置不属于评估范围，也不作为改写目标。
- `.scratch/` 在忽略规则里，评估记录不进提交。汇报结论时把数字与结果路径带上，只贴脚本跑出来的行。
- 用户对技能写法的评价与建议（「这条约束是软约束」「不该指定某个 CLI」）属于讨论：只回答，不写文件；用户给出开工指令后才进入改动，改完按第 6 步总结并等确认。
