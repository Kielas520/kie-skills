# 评审 PR

以 reviewer 身份评审别人的 PR，产出评审报告、评论草稿，并把用户确认的评论发到 PR 上。哪些问题成立、给什么修改建议、每条评论发在哪里，都由用户定夺。`<项目名称>`、`<仓库名>` 与 `<任务>` 的取值、文档目录的落点见 `kie-agent-rules` 技能目录下的 `references/workspace.md`。命令清单见 [references/github-pr-commands.md](references/github-pr-commands.md)。

## 子能力

| 子能力 | 产出 | 何时做 |
| --- | --- | --- |
| 流程一：评审报告 | `.idea/<任务>/pr-<编号>-report.md` | 用户要求评审某个 PR 时 |
| 流程二：评论草稿 | `.idea/<任务>/pr-<编号>-comments.md` | 用户在报告里定夺完问题与修改建议后 |
| 流程三：逐条确认与发送 | PR 上的一次 review 提交，含全部行内评论与总评，草稿里记录链接 | 用户确认草稿后，一条一条确认，全部确认后一次发出 |

三个流程依次进行，不合并：用户没有确认上一步的内容，不进入下一步。

## 前置条件

- 能取到 PR 的仓库与编号。用户给的是链接时从链接里取 `OWNER/REPO` 与编号；只给编号时在当前仓库查。取不到时问用户要 PR 链接。
- 目标仓库在本机的位置：按 `~/kie-ws/<项目名称>-p/source/<仓库名>/` 探测。找不到时问用户项目名称，确认后克隆到该位置，不克隆到别处。
- `<任务>` 由 PR 的 head 分支名推出：`fix/f-<ID>/...` 取 `fix/f-<ID>`，`feat/m-<ID>/...` 取 `feat/m-<ID>`，其他分支取梗概段。

## 流程一：评审报告

1. 拉取 PR 概况：标题、作者、body、base 与 head 分支、head SHA、提交列表、改动文件、CI 状态、已有的 review 与未解决 threads。已有 threads 用来避免重复提别人提过的意见。
2. 检出 head 的最新代码：在 `source/<仓库名>/` 里 `git fetch` PR 的 head，再以 detached 方式把 head SHA 挂到 `~/kie-ws/<项目名称>-p/worktrees/<head 分支名>/`；该路径已有工作区时先核对它停在 head SHA 上，不一致就 fetch 后 checkout 到 head SHA。评审只读这个工作区里的代码，不在 `source/` 里切分支。
3. 读目标仓库根目录的 `AGENTS.md` 及其引用的开发约定，作为「项目约定核对」的依据。没有就跳过这一项。
4. 读 diff 与相关的未改动代码，逐处核对：改动是否做到了 PR body 与工单声称的事、有没有超出范围的改动、正确性、边界与错误处理、并发与资源、安全、性能、测试覆盖、文档与注释是否跟着改。需要时在工作区里运行测试或构建，看真实输出。
5. 按 [assets/pr-report.md](assets/pr-report.md) 的模板与「填写要求」写评审报告。

写完把报告路径给用户。用户会在报告里判断哪些问题成立、补充自己发现的问题、改修改建议，用户口头给的定夺同步写回报告的「定夺」列。改到用户确认为止。

## 流程二：评论草稿

依据是用户定夺过的评审报告。报告不在对话里时按 `.idea/<任务>/pr-<编号>-report.md` 查找，找不到就问用户报告在哪里，不自行回到流程一重写报告，也不凭 diff 直接起草评论。

按 [assets/pr-comments.md](assets/pr-comments.md) 的模板与「填写要求」写评论草稿：只收报告里定夺为「要提」的问题，一条问题一条评论，每条标注建议的位置（行内 `path:line` 或全局）与正文。写完把路径给用户，用户决定每条是行内还是全局、改正文，改到用户确认为止。

## 流程三：逐条确认与发送

1. 逐条确认：把每条的位置与正文给用户看，用户确认一条就把草稿「状态」列改成「已确认」，再进入下一条。用户说剩下的都按草稿来时，把剩余条目一并标成已确认。确认阶段不发送任何内容。
2. 全部确认后、发送前重新取一次 head SHA。与报告里记录的不一致说明作者又推了提交，停下来告诉用户，由用户决定重新核对还是继续。
3. 核对每条行内评论的 `path` 与 `line` 落在 head 的 diff hunk 里；不在 hunk 里的评论告诉用户，改成全局评论或挂到同文件最近的改动行，由用户选。
4. 把全部已确认的行内评论与全局评论组成一次 review 提交发出，`event` 用 `COMMENT`，全局评论合并进 review 的总评正文，多条全局评论之间空一行。发送成功后把返回的 review 链接写回草稿。
5. 不提交 `APPROVE` 或 `REQUEST_CHANGES` 这类 review 结论。用户明确要求给结论时，再把 `event` 换成用户指定的结论。

## 交付

```text
━━━ PR 评审完成 ━━━
PR: {链接}
报告: {报告路径}
问题: {报告里 n 条，用户定夺要提 m 条}
评论: {一次 review 提交，行内 a 条 / 全局 b 条，链接；未发送 c 条（原因）}
review 结论: {COMMENT / 已按用户要求提交 <结论>}
工作区: {worktree 路径，停在 head SHA}
```

## Gotchas

- 行内评论的 `line` 是 head 版本文件里的行号，不是 diff 里的位置偏移，也不是 base 版本的行号。review 提交里任何一条的行不在 hunk 里，整个提交都返回 422、一条也发不出去，先逐条核对再发。
- 用户要求某一条先单独发出去时才用单条评论接口，它每发一条就通知作者一次。
- 同一个问题出现在多处时，草稿里写成一条评论挂在第一处、正文列出其余位置，不在每处各发一条。
