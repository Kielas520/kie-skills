## 填写要求

1. 「问题清单」里每一条的「依据」写从 head 代码里读到的事实（哪一行做了什么、什么输入会触发），不写推测；读不出事实的放「待确认的疑问」，不进问题清单。
2. 「位置」的行号取 head 版本文件里的行号，与 `git diff` 的 hunk 对得上；跨文件或整体设计的问题写涉及的文件与模块。
3. 严重度：必须修是改动在声称的场景下会出错、丢数据、引入安全或并发问题，或没有做到声称的事；建议修是不影响当前功能但留下明显隐患或违反项目约定；可选是可读性与一致性。风格偏好只有项目约定写明时才列入，列入时类别写「项目约定」。
4. 已有 threads 里别人提过且仍未解决的问题不重复列，在「PR 概况」的「已有评审」里计数即可。
5. 「定夺」列写报告时留空，由用户填或口头给出后同步写回：要提 / 不提（理由） / 改成（用户改过的建议）。
6. 问题按严重度从高到低排，同一严重度按文件顺序排。
7. 「测试覆盖」的「改动的行为」按改动走读里的行为逐条列，有测试的写到用例名。
