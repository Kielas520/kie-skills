## 填写要求

1. 只收报告「定夺」列为「要提」或「改成」的问题，一条问题一条评论；用户改过的建议以用户改后的为准。
2. 「建议位置」的判定：问题能落到 head 的某个 diff hunk 里的一行时建议行内，写 `path:line`；跨文件、整体设计、范围与声称不一致、测试覆盖这类问题建议全局。最终位置由用户定。
3. 评论正文用客观陈述句写三件事：哪里有什么问题、依据是什么、建议怎么改。不写「我觉得」「可能」这类不确定的措辞；拿不准的在报告里就应留在「待确认的疑问」，不进评论。
4. 建议的改法是几行内的具体替换时，正文里用 GitHub 的 `suggestion` 代码块给出可直接采纳的代码；改法涉及多处或需要作者取舍时只写做法，不给 `suggestion` 块。正文外层用四个反引号包住，正文里的代码块保持三个反引号，避免内外围栏互相截断。
5. 评论正文里不出现报告里的序号、严重度标签与「定夺」这类内部字段。
6. 「状态」列在流程三逐条确认时更新；全部发出后在「发送记录」写 review 链接与发送时间，不逐条改状态。
