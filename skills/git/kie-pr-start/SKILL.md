# 发起 PR

本地验收测试通过、分支准备交出去评审时，起草 PR body 与标题，交用户确认后建立 PR。本技能只负责起草与建 PR，不负责分支创建与推送动作本身。

## 前置条件

- 本地测试通过，报告在 `~/project/<项目名称>/.idea/test-report.md`（由 `kie-dev-test` 产出）。
- 分支上的改动已经提交。尚未提交或推送时，按用户要求执行，不擅自提交推送。
- 工单信息可以取到：单号、工单类型（需求单或缺陷单）、链接。

## PR body 结构

按 [assets/pr-body-模板.md](assets/pr-body-模板.md) 起草，四块都要有：

| 块 | 内容 |
| --- | --- |
| 关联工单链接 | `关联工作项：[<单号>](<链接>)`；无工单时写「无关联工单」 |
| 方案文档链接 | 需求单附上关联的技术方案文档链接；缺陷单在涉及架构缺陷修复时附上，复杂度不高时写「不适用」并说明原因 |
| 分支简述 | 需求单写新特性与变更内容；缺陷单写存在的问题、解决方案与变更的内容 |
| 测试报告 | 引用最后一次本地测试报告的结果，本地测试阶段没有远端结果就不写 CI 部分 |

- 工单链接与方案文档链接由用户给出，或从工单与项目知识库读取；取不到就问用户要，不编造链接。
- 分支简述按实际改动写，不复制工单原文当作变更内容。
- PR 标题按项目约定生成；项目没有约定时用 Conventional Commits 的类型前缀加一句概述，与 commit 保持一致。

## 起草与建 PR

1. 把 body 与标题草稿贴给用户确认，说明哪些内容来自工单、哪些来自测试报告。
2. 用户确认后建立 PR。是否建成 draft 由用户定，用户没说就先问一句。
3. 建 PR 之后把链接与后续步骤告诉用户：CI 跑完的远端验收走 `kie-pr-ci-test`，评审意见的处理走 `kie-pr-review-fix`。

## 交付

```text
━━━ PR 已建立 ━━━
PR: {链接}
标题: {标题}
关联工单: {单号，无则写无}
测试报告: {来自哪一份本地测试报告}
下一步: CI 跑完后走 kie-pr-ci-test 做远端产物验收
```

## 硬性约束

- 不擅自发起 PR：body 与标题先给用户看，用户确认之前不执行建 PR 的命令。
- 不擅自提交与推送。需要推送时按用户要求执行。
- 不编造工单链接、方案文档链接与测试结论。

## Gotchas

- 缺陷单不总是有方案文档，复杂度不高时不需要，别硬凑一个链接。
- 测试报告块引用 `kie-dev-test` 的最新报告，报告失效或还没写时要提醒用户先补测试。
- 远端测试结果由 `kie-pr-ci-test` 之后追加进 PR body，起草第一版时不预留空段。
- 标题与 commit 信息不一致时以用户确认为准，不自行改写标题。
