# 处理 PR 评审意见

把 PR 上的评审意见处理到推送更新并逐条回复。四个流程依次流转，每一步都要用户确认后才进行下一步。评审意见的采纳与否由用户决定，本技能不擅自提交、推送与回复。

## 前置条件

- PR 已经建立（否则走 `kie-pr-start`）。
- 当前工作区在 PR 对应的分支上。
- 能取到 PR 编号与仓库信息：

```bash
gh pr view --json number,url,headRefName,baseRefName
```

## 流程一：审核文档

产出 `~/project/<项目名称>/.idea/pr-<编号>-review.md`。

1. 拉取全部评论载体，三类都要拉，不能只看行内评论：未解决的 review threads、review body、PR 会话区的 issue comments。命令见 [references/github-pr-review.md](references/github-pr-review.md)。
2. 逐条读意见，结合当前代码实现判断状态：已经解决、需要解决、不需要改（超出改动范围、与项目约定冲突、意见本身不成立）。
3. 每个需要解决的问题给出解决方案。
4. 评估解决方案：按改动量与收益评分排序，改动尽量小、效果尽量好，从高到低排列。

文档结构：

```markdown
# PR <编号> 评审意见审核

## 问题清单

| 序号 | 来源 | 意见摘要 | 涉及文件与符号 | 状态 | 说明 |
| --- | --- | --- | --- | --- | --- |

## 解决方案

### <问题序号> <方案名>（改动量 <小/中/大>，收益 <高/中/低>）
- 做法：
- 改动的文件与符号：
- 影响面与风险：
```

写完把路径给用户，按用户意见改到确认一种方案为止，然后进入流程二。

## 流程二：实现文档

产出 `~/project/<项目名称>/.idea/pr-<编号>-fix.md`。

文档结构：

```markdown
# PR <编号> 修复实现

## 改动步骤

| 序号 | 改哪里（文件 / 符号） | 怎么改 | 验收方式 |
| --- | --- | --- | --- |

## 测试范围

| 关联问题 | 测试内容 | 命令或观察方式 |
| --- | --- | --- |
```

- 改哪里写到文件与符号一级；先后顺序按依赖排。
- 测试内容覆盖每处改动，验证改动与流程一确认的方案一致。
- 写完把路径给用户，改到用户确认为止，然后进入流程三。

## 流程三：实现与本地测试闭环

1. 按实现文档改代码，一次完成一处，跑该处的验收命令。
2. 全部改完后做本地测试闭环，走 `kie-dev-test`：报告写到 `~/project/<项目名称>/.idea/test-report.md`。
3. 验证命令失败时读完整错误输出定位根因再改，不放宽验证项。
4. 本地通过后把结果给用户，用户确认无误才进入流程四。用户要求测远端时才走 `kie-pr-ci-test`。

推送与提交按用户要求执行，不在本流程里自行推送。

## 流程四：回复评论与 PR body 校对

1. 逐条起草回复：说明改了什么、解决了哪条意见、对应的 commit。意见不采纳时说明技术理由，不做表演性回复。
2. 一条一条交用户确认后发送。用户说全部回复时直接发送剩余回复。
3. 核对 PR body 与当前实现的描述是否冲突：本地测试结果、远端测试结果会改变 PR body 的测试报告段。有冲突或需要补充时，把要改的内容给用户看，确认后修改。

## 交付

```text
━━━ 评审处理完成 ━━━
PR: {链接}
已解决: {n} 条 / 待解决 {m} 条
不采纳: {n} 条（附理由）
测试: 本地 {通过 / 未通过}{，远端 {结果}}
回复: {已发送 n 条 / 待确认}
PR body: {已更新 / 无需变更}
```

## 硬性约束

- 不擅自提交、推送、发布评论：每个动作都先给用户看内容。
- 不盲目采纳 bot 建议：先在代码里验证技术合理性，与项目约定冲突时给技术理由拒绝。
- 不改测试与断言迁就实现。
- 流程之间不合并：用户没有确认上一步的内容，不进入下一步。

## Gotchas

- 评审意见有三类载体，只拉行内 threads 会漏掉 review body 与 PR 会话区的意见。
- 拉取要用 GraphQL 才能拿到 `isResolved` 状态；分页要走到 `hasNextPage` 为 false，避免截断第 50 条之后的意见。
- review 端点返回历史全量，同一个评审者只按最新一条 review 的 state 判定，避免复活已经销账的意见。
- 用户可能在中途改动代码，动手前重读受影响文件，基于当前内容继续。
- 回复里带上 commit 号，评审者才能对上改动。
