# 处理 PR 评审意见

把 PR 上的评审意见处理到逐条回复。评审意见采纳与否由用户决定。`<项目名称>` 与 `<任务>` 的取值、文档目录的落点见 `kie-agent-rules` 技能目录下的 `references/workspace.md`。命令清单见 [references/github-pr-review.md](references/github-pr-review.md)。

## 子能力

| 子能力 | 产出 | 何时做 |
| --- | --- | --- |
| 流程一：审核文档 | `.idea/<任务>/pr-<编号>-review.md` | 用户要求处理评审意见时 |
| 流程二：实现文档 | `.idea/<任务>/pr-<编号>-fix.md` | 用户确认审核文档里的方案后 |
| 流程三：实现与逐处验收 | 代码改动与每处的验收结果 | 用户确认实现文档后 |
| 流程四：回复评论与核对 PR body | 回复草稿、发送的回复、需要时改好的 PR body | 用户确认实现结果后 |

四个流程依次进行，不合并：用户没有确认上一步的内容，不进入下一步。

## 前置条件

- 能取到 PR 编号与仓库信息：

  ```bash
  gh pr view --json number,url,headRefName,baseRefName
  ```

  取不到时说明找不到对应的 PR，问用户 PR 编号。
- 当前工作区在 PR 对应的分支上。

## 流程一：审核文档

1. 拉取全部评论载体，三类都要拉，不能只看行内评论：未解决的 review threads、review body、PR 会话区的 issue comments。
2. 逐条读意见，结合当前代码实现判断状态，每个需要解决的问题给出解决方案并排序。
3. 按 [assets/pr-review.md](assets/pr-review.md) 的模板与「填写要求」写审核文档。

写完把路径给用户，按用户意见改到确认方案为止。

## 流程二：实现文档

按 [assets/pr-fix.md](assets/pr-fix.md) 的模板与「填写要求」写实现文档。写完把路径给用户，改到用户确认为止。

## 流程三：实现与逐处验收

1. 按实现文档改代码，一次完成一处，跑该处的验收命令，看真实输出。
2. 验收命令失败时读完整错误输出定位根因再改，不放宽验证项，不改测试与断言迁就实现。
3. 全部改完后把每处的验收结果给用户，问用户要不要做本地验收测试、生成测试报告。

## 流程四：回复评论与核对 PR body

1. 先确认改动有没有提交并推送。还没有时告诉用户：回复里要写对应的 commit，评审者在 PR 上能看到这个 commit 之后回复才对得上；等用户提交并推送后再填 commit 号。
2. 逐条起草回复：说明改了什么、解决了哪条意见、对应的 commit。意见不采纳时说明技术理由。不写只表态、不说明改了什么的回复（例如「好的，已修改」）。
3. 一条一条交用户确认后发送。用户说全部回复时，直接发送剩余回复。
4. 核对 PR body 与当前实现是否冲突：代码改动与验证结果会改变验证段，实现范围变化让改动、影响两段失实时一并更新。评审修复的往来、回复与「按评审意见修改」这类说明留在评论里，不写进描述，描述里只留改动本身。有冲突或需要补充时，把要改的内容给用户看，确认后修改。

## 交付

```text
━━━ 评审处理完成 ━━━
PR: {链接}
已解决: {n} 条 / 待解决 {m} 条
不采纳: {n} 条（附理由）
验收: {每处验收结果；本地验收测试 已做 / 未做}
回复: {已发送 n 条 / 待确认}
PR body: {已更新 / 无需变更}
```
